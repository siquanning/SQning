# 杭州麻将 — 产品需求文档

> 纯前端实现，单机人机对战。4 人局，固定白板财神，自摸胡。

---

## 一、基础规则

### 1.1 牌具

- 136 张标准麻将牌（万/条/筒各 1-9×4 = 108，东南西北中发白 × 4 = 28）
- 无花牌（春/夏/秋/冬/梅/兰/竹/菊）
- **白板 = 财神**，共 4 张，可替代任何牌凑顺子/刻子/对子

### 1.2 座次

- 4 人局：庄家 → 南家（庄下家）→ 西家 → 北家
- 庄家由开局骰子决定，胡牌者成为下一局庄家

### 1.3 行牌

- 庄家 14 张起手，闲家 13 张起手
- 逆时针摸牌，逆时针出牌
- **优先级**：碰/杠 > 吃，吃只能吃上家
- 碰/杠不需要亮财神
- 只有庄家下家吃庄家牌时需要先亮财神，否则不能吃；其他闲家之间吃牌无需亮

### 1.4 杠

- 明杠、暗杠、加杠均从**牌墙倒数第二张**补牌
- 牌墙倒数第一张翻开公示，仅供查看
- 杠上开花：杠后补牌直接自摸胡 → 算一个牌型（多一倍）

### 1.5 流局

- 牌墙摸完无人胡 → 流局，**原庄家连庄**，重新洗牌

### 1.6 胡牌条件

- 基础门清：4 组面子（顺子/刻子）+ 1 对将牌
- **只能自摸胡，无放炮**
- 财神可替代任意牌（可用于面子或参与将牌）

## 二、牌型（番种）

### 2.1 牌型列表

| # | 牌型 | 说明 |
|:--:|------|------|
| 1 | **平胡** | 基础胡牌（4面子+1将），基数 1 倍 |
| 2 | **七对** | 7 个对子，不能有杠 |
| 3 | **豪华七对** | 七对中有四张相同牌拆成两个对子（如 1万×4 → 两个 1万对） |
| 4 | **碰碰胡** | 全刻子（对对胡），4 刻子 + 1 对将 |
| 8 | **十三幺** | 13 种幺九牌各一 + 任意一张凑对；白板算幺九牌之一，其他白板当赖子 |
| 9 | **杠上开花** | 杠后补牌直接胡 |
| 10 | **爆头** | 手牌 1 张财神 + 牌型成型（听牌），摸任意牌可胡 |
| 11 | **天胡** | 庄家起手 14 张直接胡 |
| 12 | **地胡** | 闲家起手听牌，第一轮摸牌即胡 |
| 13 | **大四喜** | 东南西北四风各成刻子 |
| 14 | **小四喜** | 三门风刻 + 一对风 |
| 15 | **大三元** | 中发白各成刻子（白板当作财神时算白刻子） |
| 16 | **小三元** | 二门箭刻 + 一对箭 |

### 2.2 倍数叠加规则

- **叠加乘法**，无封顶
- 每多一个牌型，倍率翻倍
- 爆头本身算一个牌型参与叠加
- 例：闲家爆头 + 清一色 = 1×2×2 = 4 倍

### 2.3 特别说明

- **抢杠胡不算**
- **七对不能有杠**（暗杠也不能拆成两个对子）
- 十三幺中白板既是幺九牌之一，多余白板当赖子

## 三、爆头 & 飘财

### 3.1 爆头

- **前置条件**：手中**仅 1 张**财神牌，且手牌已成型（听牌状态）
- **胡牌方式**：摸到任意牌后直接自摸胡
- **倍率**：平胡 × 2
- **对他人**：无限制

### 3.2 飘财（财飘）

- **前置条件**：手中**至少 2 张**财神，摸牌后已能胡牌（暴头状态）
- **操作**：放弃立即胡牌，主动打出一张财神牌（保留刚摸的牌），使手牌进入暴头听牌（1财神作将 + 4副完整面子）
- **后续**：
  - 飘财者跳过本轮，其他三人各摸打一轮（摸牌 + 弃牌）
  - 期间三家只能 **摸打、暗杠**，不能吃、碰、明杠
  - 但三家**可以自摸胡**
  - 无人胡则轮回到飘财者，摸任意牌后自动爆头胡牌
- **倍率**：
  - 一飘（打出一张财神后胡）：4 倍
  - 二飘（打出两张财神后胡）：8 倍
  - 三飘（打出三张财神后胡）：16 倍（手中 ≥4 张财神 → 打出 3 张 → 留 1 张爆头）
- **叠加**：飘财倍数与牌型叠加（乘法）

## 四、四风连打

### 触发条件

- 开局后，从庄家开始，四家按顺序打出的**第一张牌**恰好都是同一种风牌
- 例如：庄家打东 → 下家打东 → 对家打东 → 上家打东

### 处理

- 庄家掷两个骰子，两个骰子点数和记为 N
- 庄家向每个闲家各支付 **N 分**
- 本局作废，**重新洗牌开新局**（庄家不变）

## 五、计分规则

### 5.1 基础分

| 场景 | 庄家 | 闲家 |
|------|:---:|:---:|
| **庄家自摸** | 赢得 `3 × 8 × 倍率` 分 | 每人支付 `8 × 倍率` 分 |
| **闲家自摸** | 支付 `8 × 倍率` 分 | 另两闲家各支付 `1 × 倍率` 分，胡牌闲家赢得 `8 + 1 + 1` × 倍率 |

### 5.2 示例

闲家七对+清一色自摸（倍率 = 1×2×2 = 4 倍）：
- 庄家付：8 × 4 = **32 分**
- 另两闲家付：1 × 4 = **4 分/人**
- 胡牌者得：32 + 4 + 4 = **40 分**

庄家自摸爆头+杠上开花（倍率 = 1×2×2 = 4 倍）：
- 三闲家各付：8 × 4 = **32 分**
- 庄家得：96 分

- 网络对战

- 纯前端 HTML/CSS/JS + ES Modules
- 无框架依赖
- 教练 AI 重量计算用 Web Worker，不阻塞 UI 线程

## 八、教练模式（Coach Mode）

### 8.1 产品定位

在普通模式基础上提供实时 AI 辅助分析，帮助玩家通过**即时决策反馈 + 战后复盘**，形成长期盈利的"肌肉记忆"——在输赢波动中动态调整策略。

核心原则：
- **授人以渔**：不只给答案，更解释背后的逻辑
- **实时可用**：所有推理在浏览器本地完成，每回合响应 < 1 秒
- **无干扰**：分析面板可折叠/悬浮，不遮挡牌桌

### 8.2 启动与开关

- 开局前可选"普通模式"或"教练模式"
- 教练模式下默认开启辅助面板，可随时折叠
- 对局中可切换模式（普通 ⇄ 教练），切换后不影响牌局进程

### 8.3 辅助分析面板 — UI

- **默认位置**：右侧侧边栏，宽度约 320px，可拖拽调整
- **悬浮模式**：窄屏（移动端）自动切换为悬浮按钮 + 弹窗
- **内容分区**：四层信息以折叠卡片形式展示，默认全部展开

#### 最小化与"先判断后对答案"机制

教练模式的核心教学理念是"先自己做决策，再看答案"。面板默认行为：

- **摸牌后**：面板自动最小化（仅显示标题栏），玩家先自己判断该打哪张
- **弃牌后**：面板自动展开，显示本轮分析结果，供玩家对照验证
- **手动控制**：玩家可随时最小化/展开面板，也可在设置中切换为"始终展开"
- **最小化状态**：仅显示一行提示文字"打出牌后显示分析"，不暴露任何建议内容

此机制保证每轮的学习闭环：独立判断 → 操作执行 → 对照答案 → 理解差距。

#### 更新时机
- 每次轮到玩家出牌时，后台计算分析结果但面板保持最小化
- 玩家弃牌后，面板自动展开展示本轮分析
- 其他玩家操作后刷新面板（如面板当前处于展开状态）
- 玩家可随时点击"分析"按钮手动展开查看

### 8.4 辅助分析 — 消息流（替代固定四层）

不用固定的四层卡片，改为**消息流**——像真人教练坐在旁边，局面需要什么就说什么。每轮默认只给一条核心建议，不把全部信息堆上来。

#### 消息类型

教练消息分五类，按情境推送，不是每轮全发：

| 类型 | 触发情境 | 示例 |
|------|---------|------|
| **弃牌建议** | 每轮必定生成，但最小化状态下隐藏 | "建议打 3 万。留 7-8 万搭子，清一色方向不要拆。" |
| **方向分析** | 手牌方向模糊 / 进入中盘 / 玩家手动请求 | "当前最可行的两个方向：碰碰胡（距听牌差 2 步）、平胡速听（差 1 步）。清一色剩余万子太少，不建议追。" |
| **威胁预警** | 某家碰/杠、牌河出现关键张、推测有人听牌 | "对家可能已听牌（刚碰了 8 筒后直接打出 3 万生张），你要小心万字生张。" |
| **时机提醒** | 满足爆头/飘财/可转牌型等条件 | "你手牌已成型，1 张财神在握——摸任意牌即可爆头胡。但如果想追更高倍率，可以考虑飘财。" |
| **深度解析** | 关键决策点（听牌临界、飘财抉择、大牌分岔口）| 完整展开：当前局面 → 可选路径 → 每条路径的胜负预估 → 推荐理由 → 反例对比 |

#### 消息优先级

威胁预警 > 时机提醒 > 弃牌建议 > 方向分析。高优先级消息立刻弹出（即使面板最小化也弹出浮层提示），低优先级消息排队展示。

#### 消息结构

每条消息由三档信息构成，玩家可按需展开：

```
┌─────────────────────────────────┐
│ 💡 建议打 3 万                   │  ← 一句话结论（始终可见）
│   留 7-8 万搭子等清一色           │
│                                 │
│   ▶ 展开看推理过程               │  ← 点击展开
│   ┌─────────────────────────┐   │
│   │ 手牌万子 9 张（含 2 个搭子）→   │
│   │ 弃 3 万不破坏任何搭子结构，     │
│   │ 反倒是 3 万孤张留也没用。       │
│   │ 条子方向只剩 5 张 → 放弃。      │
│   │ [牌效基础] [方向判断]         │  ← 知识标签
│   └─────────────────────────┘   │
└─────────────────────────────────┘
```

- **一句话结论**：始终可见，不打牌也能看
- **展开推理过程**：自然语言解释，附带知识标签
- **扩展到完整对比**：在关键决策点，可进一步展开为路径对比（选 A vs 选 B 的优劣）

#### 与"先判断后对答案"的配合

- 玩家摸牌 → 面板自动最小化，消息在后台生成但不展示
- 玩家弃牌 → 面板展开，弹出本轮"弃牌对比"（你打了 X，教练推荐了 Y）
- 若玩家选择与 AI 一致 → 简略确认 + 一句推理要点
- 若玩家选择与 AI 不同 → 展开完整推理，解释差异原因
- 过程中若有威胁预警 → 即时弹窗浮层（即使面板最小化），不等到弃牌后

### 8.5 分析措辞规范

- 使用"建议""推荐"而非"必须""一定"
- 概率表达用高/中/低三级，不为追求精准而编造百分比
- 不得使用游戏术语时附简短解释（如"搭子：连续两张或间隔一张的同花色牌"）
- 避免评价性语言（"你这手打错了"→"这张牌有更好的替代方案"）

## 九、战后复盘与习惯学习

### 9.1 局后复盘

每局结束后，教练系统自动生成复盘报告：

| 复盘内容 | 说明 |
|----------|------|
| **本局数据概览** | 胡牌者、最终倍率、各家得分变化、本局轮数 |
| **关键决策点** | 标记本局中的关键分岔路口（如拆错搭子、错失转张时机、过度保守放弃机会牌型） |
| **决策对比** | 每个关键点展示"你的选择" vs "推荐选择"，附分析 |
| **亮点记录** | 标注本局中符合最优策略的优秀决策 |

### 9.2 历史牌谱存储

每局自动保存牌谱（JSON 格式），包含：

```
牌谱结构:
├── 基本信息（时间、模式、各家位置/座位）
├── 初始手牌（每家 13/14 张）
├── 每步操作记录
│   ├── 玩家: 摸牌、弃牌、吃/碰/杠/胡
│   ├── 时间戳
│   └── [教练模式下] 当时的分析快照
├── 最终结果（谁胡、牌型、倍率、得分变化）
└── 复盘标记（关键决策点列表）
```

存储方式：IndexedDB，支持导出/导入 JSON 文件。

### 9.3 长期统计看板（玩家画像）

基于历史牌谱数据，持续更新玩家打牌习惯画像：

| 统计维度 | 指标 |
|----------|------|
| **贪大牌倾向** | 追大牌（清一色/碰碰胡/七对）成功率、主动放弃大牌转平胡的频率 |
| **防守风格** | 危险牌弃出率、对手听牌时转为防守的时机 |
| **弃牌效率** | 弃牌后被他家吃/碰/杠的比率、弃牌顺序模式正确率 |
| **牌型偏好** | 各牌型尝试频率及成功率 |
| **财神利用率** | 爆头/飘财成功率和时机选择 |

### 9.4 习惯识别与针对性提示

系统自动识别不良倾向，在后续对局中针对性地给出提示：

| 识别的不良倾向 | 触发条件 | 针对性提示示例 |
|---------------|----------|---------------|
| **贪大牌率过高** | 近 10 局追大牌占比 > 70% 且成功率 < 30% | "你最近追大牌比较激进，当前局建议优先听牌求稳" |
| **防守消极** | 对手听牌后你继续进攻的比例 > 80% | "对家大概率已听牌，建议本手优先处理危险牌" |
| **弃牌模式错误** | 连续多局拆搭顺序有问题 | "你倾向于先拆边搭再拆卡搭，但当前手牌建议反向" |
| **财神运用保守** | 飘财机会出现但从未使用 > 10 局 | "当前手牌满足一飘条件，考虑飘财博取更高倍率" |

### 9.5 数据本地化承诺

- 所有牌谱、统计数据、学习模型均在本地存储
- 不收集、不上传、不依赖任何云端服务
- 玩家可随时导出/清除所有数据

## 十、教练 AI — 技术架构

### 10.1 核心原则：教练与对手共享同一引擎

教练 AI 和对手 AI **使用同一套 ISMCTS 搜索引擎**（见第十一节），不维护两套独立的分析逻辑。

- **对手 AI**：跑 ISMCTS → 选胜率最高的动作 → 执行
- **教练 AI**：跑 ISMCTS（从玩家视角）→ 从搜索树中提取可读的洞察 → 翻译成自然语言

这意味着教练给出的建议，和对手 AI 在相同局面下做决策用的信息，是**同一质量的**。不会出现"教练说打 A，但 AI 对手其实会打 B"的情况。

### 10.2 核心模块（简化后的架构）

```
教练 AI = ISMCTS 引擎（从玩家视角搜索）+ 搜索解释器 + NL 生成器
│
├─ 🧠 ISMCTS 搜索核心 (src/ai/ismcts.js) ← 共用
│   └─ 从人类玩家视角运行 ISMCTS，产出搜索树
│
├─ 🔍 搜索解释器 (src/coach/search-interpreter.js) ← 教练专属
│   ├── TOP-K 动作提取（搜索树中访问次数最多的 K 个动作及其胜率）
│   ├── 威胁检测（对手信念模型中哪些对手的听牌概率 > 阈值）
│   ├── 方向分歧识别（两条路径胜率接近但方差大 → 关键分岔口）
│   ├── 飘财窗口判断（飘财 vs 直接胡的模拟胜率对比）
│   └── 搜索置信度（模拟次数够不够、结果稳不稳定）
│
├─ 💬 自然语言解释器 (src/coach/nl-explainer.js) ← 教练专属
│   ├── 5 类消息模板库（弃牌建议/方向分析/威胁预警/时机提醒/深度解析）
│   ├── 搜索统计 → 自然语言映射（胜率 65% → "较高把握"）
│   ├── 上下文拼接（手牌 + 胜率排序 + 对手状态 → 完整句子）
│   ├── 知识标签附加（[牌效基础] [方向判断] [防守博弈]）
│   └── 措辞规范（"建议"非"必须"，概率用高/中/低三级）
│
└─ 🎚 分析深度分档
    ├─ 简略模式（仅 TOP-1 建议 + 一句话理由，< 100ms）
    ├─ 标准模式（TOP-3 对比 + 威胁简报，< 300ms）
    └─ 深度模式（完整搜索树分析 + 路径推演 + 完整对比，< 1s）
```

### 10.3 搜索解释器：从 ISMCTS 树到教练洞察

ISMCTS 搜索完成后产出一棵搜索树。搜索解释器负责从中提取教练需要的信息：

| 搜索树信息 | 教练洞察 | 对应消息类型 |
|-----------|---------|:--:|
| 各候选动作的模拟胜率排序 | "建议打 X，胜率最高 62%" | 弃牌建议 |
| 某候选胜率相近但方差大 | "两个方向胜率接近，这是关键分岔口" | 深度解析 |
| 打出某张牌后对手胜率显著上升 | "打 3 万危险——对手需求万子的概率高" | 威胁预警 |
| 某对手信念模型听牌概率 > 70% | "对家大概率已听牌" | 威胁预警 |
| 飘财 vs 直接胡的胜率对比 | "飘财博 4 倍，胜率从 80% 降至 55%，值得冒这个险" | 时机提醒 |
| 当前手牌向听数 + 各牌型可达性 | "当前距听牌差 1 步，七对子余 6 张可用" | 方向分析 |

**关键优势**：不再需要手动设权重（牌效×0.4 + 安全×0.3...）——这些"权重"由 ISMCTS 的数千次模拟**自动学习**出来。搜索树天然反映了牌效、安全、方向的一切权衡。

|------|------|------|
| 简略分析耗时 | < 100ms | 仅提取 TOP-1 + 一句话 |
| 标准分析耗时 | < 300ms | TOP-3 + 威胁简报 |
| 深度分析耗时 | < 1s | 完整搜索 + 路径对比 |

| 牌谱存储容量 | IndexedDB > 1000 局 | 含每局 ISMCTS 分析快照 |
| 内存占用 | < 50MB | 搜索树复用 + TypedArray 存储 |

## 十一、对手 AI — ISMCTS 搜索引擎

### 11.1 设计目标

三家 AI 对手必须具备真正的战术深度，而非简单规则。核心要求：

- **不完全信息推理**：在看不到对手手牌和牌墙顺序的前提下，做出接近最优的决策
- **多步前瞻**：不只评估当前回合，而是推演到终局
- **难度可调**：简单/普通/困难三档，用统一的算法框架调控
- **浏览器可行**：单次决策 < 1 秒，Web Worker 中执行，不阻塞 UI

### 11.2 算法选型：ISMCTS

**Information Set Monte Carlo Tree Search（信息集蒙特卡洛树搜索）** 是目前在不完全信息博弈中证明有效的标准算法。它模拟人类高手的思维过程：

> 对手大概是什么牌 → 我打哪张 → 接下来会怎么发展 → 谁赢

核心流程：

```
ISMCTS 每次决策：
1. Determinization（确定化采样）
   → 随机生成 N 种"可能的真实局面"
   → 对手手牌 + 剩余牌墙顺序，均符合已观察信息

2. 对每种采样局面，进行 MCTS 搜索：
   ├─ Selection  → UCB1 选择最有探索价值的节点
   ├─ Expansion  → 展开未访问过的动作
   ├─ Rollout    → 快速模拟到终局（贪婪策略）
   └─ Backprop   → 胜负结果反向传播

3. 聚合所有采样的搜索结果
   → 选平均胜率最高的动作
```

**为什么选 ISMCTS 而不是深度学习**：
- 纯浏览器环境，无法跑 GPU 推理
- 不需要训练数据，零样本即可工作
- 难度通过模拟次数直接调控，可解释性强
- 杭州麻将规则（只能自摸）比日麻简单，模拟速度更快

### 11.3 架构分层

```
对手 AI 引擎 (Web Worker: src/ai/ai-worker.js)
│
├─ 🧠 ISMCTS 搜索核心 (src/ai/ismcts.js)
│   ├─ Determinization: 采样符合观测的对手手牌+牌墙
│   ├─ Selection: UCB1 选择展开节点
│   ├─ Expansion: 展开合法动作
│   ├─ Rollout: 快速模拟到终局 (>2000局/秒)
│   └─ Backprop: 反向传播胜负结果
│
├─ ⚡ 快速游戏模拟器 (src/ai/game-sim.js)
│   ├─ 轻量版 GameState（位图表示136张牌）
│   ├─ 快速 Shanten 计算（预计算查表，<1μs）
│   ├─ 贪婪 Rollout 策略（每步选 Shanten 下降最快的动作）
│   └─ 终局判定（胡牌/流局）
│
├─ 👤 对手信念模型 (src/ai/opponent-model.js)
│   ├─ 基于弃牌序列的花色分布推断
│   ├─ 吃碰杠暴露的面子反推手牌结构
│   ├─ Determinization 采样权重（更可能的局面采样更多）
│   └─ 增量更新（每次新信息到达时更新信念）
│
└─ 🎚 难度分档 (src/ai/difficulty.js)
    ├─ 简单: 500 次模拟 + 15% 随机噪声
    ├─ 普通: 1500 次模拟 + 5% 随机噪声
    └─ 困难: 3000 次模拟 + 0% 噪声
```

### 11.4 性能指标与可行性

| 指标 | 目标 | 说明 |
|------|:----:|------|
| 单次决策耗时 | < 1s（困难）| Web Worker 异步，UI 无感知 |
| 模拟速度 | > 2000 局/秒 | 位图表示 + Shanten 查表 |
| 确定性采样数 | 3-5 个/决策 | 每个采样内跑 600-1000 次 MCTS |
| 内存占用 | < 20MB | 位图状态 + 搜索树节点复用 |

**为什么浏览器可行**：

- **位图表示**：136 张牌用 4 个 `Uint32Array` 表示，拷贝极快（<1μs）
- **Shanten 查表**：34 种牌的向听数预计算到 TypedArray，O(1) 查询
- **Rollout 极简**：每步只评估 Shanten 变化，不做完整手牌分析
- **树节点复用**：每次决策后复用上一轮的搜索树子树，加速后续决策
- **时间预算**：`performance.now()` 检查，到时间立即返回当前最优

### 11.5 与引擎接口的关系

engine.js 的 AI 函数签名不变，内部实现切换为 ISMCTS：

```js
// engine.js — AI 函数内部委托给 ISMCTS 引擎
export function chooseDiscard(hand, playerId, gameState) {
  return aiWorker.chooseDiscard(hand, playerId, gameState);
}

export function shouldPeng(playerId, tile, gameState) {
  return aiWorker.shouldClaim(playerId, "peng", tile, gameState);
}
// ... 其余 AI 函数同理
```

ISMCTS 引擎对每个候选动作执行搜索，比较胜率，决定是否吃/碰/杠。碰/杠的决策本质上就是"碰了→弃牌→模拟到终局" vs "不碰→摸牌→模拟到终局"，直接比较胜率。

### 11.6 教练模式中的复用

ISMCTS 引擎的以下组件被教练 AI 复用：

- **快速游戏模拟器** → 教练"深度解析"中的路径推演
- **对手信念模型** → 教练"威胁预警"
- **Shanten 查表** → 教练手牌评估

避免维护两套独立的分析逻辑，教练 AI 的"建议"和对手 AI 的"决策"基于同一套底层引擎。
